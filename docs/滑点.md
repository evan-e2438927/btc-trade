## 1. 什么是滑点

**滑点**（Slippage）是指你**预期成交的价格**与**实际成交的价格**之间的差异。

### 通俗类比

> 想象你去超市买一件标价 100 元的商品，但结账时收银员告诉你现在涨价到 102 元——这 2 元的差距就是"滑点"。

在交易市场中：

```
你看到 BTC 价格是 65000 USDT，点击"立即买入"
      ↓
从发出指令到系统执行，市场价变成了 65080 USDT
      ↓
实际以 65080 成交 → 滑点 = 80 USDT
```

---

## 2. 滑点的产生原因

### 2.1 市场价格持续波动

加密货币市场 7×24 小时运转，价格每毫秒都在变化。从你"看到价格"到"订单实际执行"之间，哪怕只有几十毫秒，价格也可能已经变动。

```
时间轴：

T+0ms   你看到价格 65000，决定买入
T+5ms   你点击「买入」按钮
T+20ms  网络传输，服务器收到请求
T+25ms  系统读取当前价格：已变为 65050
T+25ms  以 65050 成交

滑点 = 65050 - 65000 = 50 USDT
```

### 2.2 订单簿深度不足（大单冲击）

真实交易所使用[**订单簿**撮合](./订单簿撮合.md)：市场上有很多"挂单"在不同价格等待成交。当你的买单数量超过当前最优价位的挂单数量时，系统会依次"吃掉"更高价位的挂单。

```
卖方订单簿（Ask）：
  65100  ×  0.5 BTC
  65050  ×  0.3 BTC   ← 0.3 BTC 在此价成交
  65000  ×  0.2 BTC   ← 先吃这里的 0.2 BTC

你想买 0.5 BTC（市价单）：
  0.2 BTC × 65000 = 13000 USDT
  0.3 BTC × 65050 = 19515 USDT
  ──────────────────────────────
  平均成交价 = 32515 / 0.5 = 65030 USDT

预期价格：65000，实际均价：65030 → 滑点 = 30 USDT/BTC
```

### 2.3 网络延迟

从用户发出请求到交易所执行，中间经过网络传输、排队处理等环节，每个环节都可能引入延迟，延迟越大，价格漂移越多。

---

## 3. 滑点的计算方式

### 绝对滑点

```
绝对滑点 = 实际成交价 - 预期价格
```

### 相对滑点（百分比）

$$
\text{滑点\%} = \frac{\text{实际成交价} - \text{预期价格}}{\text{预期价格}} \times 100\%
$$

**举例**：
- 预期价格：65000 USDT
- 实际成交：65130 USDT
- 绝对滑点：+130 USDT
- 相对滑点：$\frac{130}{65000} \times 100\% \approx 0.2\%$

---

## 4. 正滑点与负滑点

| 类型 | 方向 | 含义 | 对用户影响 |
|------|------|------|-----------|
| **负滑点**（Negative Slippage） | 买单：实际价 > 预期价<br>卖单：实际价 < 预期价 | 成交价对你不利 | 亏损更多 / 收益减少 |
| **正滑点**（Positive Slippage） | 买单：实际价 < 预期价<br>卖单：实际价 > 预期价 | 成交价对你有利 | 比预期更划算 |

```
买入场景：

预期价  实际成交价  滑点类型
65000  →  65200   负滑点（多花了 200 USDT）
65000  →  64800   正滑点（少花了 200 USDT）
```

> 实际上绝大多数情况是负滑点，正滑点较少出现。

---

## 5. 影响滑点大小的因素

| 因素 | 对滑点的影响 | 说明 |
|------|------------|------|
| **交易品种波动性** | 波动越大 → 滑点越大 | BTC 在大行情时滑点明显增加 |
| **订单大小** | 订单越大 → 滑点越大 | 大单会"吃穿"多个价格层级 |
| **市场流动性** | 流动性越低 → 滑点越大 | 小币种比 BTC 滑点大得多 |
| **网络延迟** | 延迟越高 → 滑点越大 | 服务器离交易所越远影响越大 |
| **订单类型** | 市价单 > 限价单 | 限价单指定价格，理论上无负滑点 |
| **市场时段** | 清淡时段 → 滑点较大 | 流动性差时订单簿深度不足 |

---

## 6. 限价单 vs 市价单的滑点差异

```
市价单（Market Order）：
  ✅ 一定成交
  ❌ 价格不可控
  ❌ 存在滑点风险（尤其大单或波动行情）

限价单（Limit Order）：
  ✅ 价格完全可控（不会以更差的价格成交）
  ✅ 无负滑点（要么按指定价成交，要么不成交）
  ❌ 不保证成交（价格必须到达指定位置）
```

**结论**：限价单是规避滑点的最有效方式，代价是可能无法成交。

## 7. 本系统中的滑点处理

### 当前实现（简化模型）

本系统作为教学/模拟交易系统，对滑点进行了**简化处理**：

```typescript
// lib/orderService.ts
// 市价单：直接读取 priceStore 的当前价，以该价格成交
// 不模拟订单簿深度，不引入随机滑点
const currentPrice = priceStore.getPrice();
await fillOrder(order, currentPrice);
```

**特点**：
- 市价单以下单瞬间的 `priceStore` 价格成交
- 没有模拟订单簿深度冲击
- 没有随机价格漂移
- 实际上是**零滑点**的理想化模型

### 真实交易所中的处理

| 机制 | 说明 |
|------|------|
| **最大滑点保护** | 用户可设置可接受的最大滑点比例，超出则拒绝成交 |
| **订单簿撮合** | 按价格优先、时间优先依次匹配挂单 |
| **部分成交** | 大单可能被拆分，在不同价格层级分批成交 |

### 如果要在本系统中模拟滑点

可以在 `fillOrder` 中添加随机扰动：

```typescript
// 模拟 ±0.1% 的随机滑点
function applySlippage(price: number, side: 'buy' | 'sell'): number {
  const slippageRate = (Math.random() * 0.001); // 0 ~ 0.1%
  // 买单：价格偏高（对用户不利）
  // 卖单：价格偏低（对用户不利）
  return side === 'buy'
    ? price * (1 + slippageRate)
    : price * (1 - slippageRate);
}
```

## 8. 如何减少滑点影响

| 策略 | 说明 |
|------|------|
| **使用限价单** | 指定价格，杜绝负滑点 |
| **分批下单** | 大额订单拆成小单，减少价格冲击 |
| **选择流动性好的交易对** | BTC/USDT 流动性远好于小币，滑点更小 |
| **避开极端行情** | 暴涨暴跌时市场波动剧烈，滑点显著放大 |
| **设置滑点容忍度** | 在 DeFi（去中心化交易所）中尤为重要 |

---

## 总结

```
滑点 = 预期价格与实际成交价格的差距

产生原因：
  ├── 市场价格波动（时间差）
  ├── 订单簿深度不足（大单冲击）
  └── 网络/系统延迟

规避方式：
  ├── 使用限价单（最有效）
  ├── 分批执行大单
  └── 在流动性充足时交易

本系统：简化实现，市价单以当前 priceStore 价格零滑点成交
```
