## 1. 什么是部分成交

**部分成交**（Partial Fill）是指一笔订单委托的数量，在一次或多次撮合中**只成交了其中一部分**，剩余数量继续挂单等待。

### 通俗类比

> 你在二手市场挂单"收购 10 个苹果，出价 5 元/个"。
> - 第一个卖家只有 3 个苹果，先卖给你 3 个 → **部分成交**
> - 第二个卖家来了，卖给你 5 个 → 累计成交 8 个，**仍未全部成交**
> - 第三个卖家来了，卖给你剩余 2 个 → 累计 10 个，**全部成交**
>
> 整个过程只有**一张收购单**，但产生了**3 条成交记录**。

---

## 2. 部分成交的产生原因

部分成交只发生在**有真实订单簿**的场景中，对手方挂单数量不足时就会出现：

```
你的限价买单：1.0 BTC @ 65000

当前卖盘（Ask）@ 65000：
  张三：0.3 BTC
  李四：0.5 BTC
  王五：0.2 BTC（稍后才挂上来）

撮合过程：
  T1：匹配张三 → 成交 0.3 BTC，剩余 0.7 BTC 等待
  T2：匹配李四 → 成交 0.5 BTC，剩余 0.2 BTC 等待
  T3：王五挂单 → 成交 0.2 BTC，订单完全成交
```

**本质原因**：你想买的量 > 当前价位上卖方的挂单总量。

## 3. 订单时效策略（GTC / IOC / FOK）

下单时可以指定"没吃完怎么办"，这由**时效策略**（Time In Force）控制：

| 策略 | 全称 | 部分成交时的处理 | 适用场景 |
|------|------|----------------|---------|
| **GTC**（默认）| Good Till Cancel | 已成交部分生效，**剩余继续挂单**，直到全部成交或手动撤单 | 普通限价单，不急 |
| **IOC** | Immediate Or Cancel | 立即撮合能成交的部分，**剩余直接取消** | 想尽量成交但不要长时间挂单 |
| **FOK** | Fill Or Kill | 必须**全部成交**，否则整单取消，零容忍部分成交 | 大单，必须全部拿到 |

### 三种策略的行为对比

```
场景：你挂买单 1.0 BTC @ 65000，卖盘只有 0.3 BTC

GTC：成交 0.3 BTC，剩余 0.7 BTC 继续挂着 ⏳
IOC：成交 0.3 BTC，剩余 0.7 BTC 立即取消 ❌
FOK：整单取消，0.3 BTC 也不成交 ❌
```

## 4. 币安的完整处理机制

### GTC 订单的部分成交流程（最常见）

```
你挂限价买单：1.0 BTC @ 65000（GTC）
当前卖盘 @ 65000 只有 0.3 BTC

────────────────────────────────────────────────────────
第一次撮合（0.3 BTC 成交）：

  UPDATE orders
  SET executed_quantity = 0.3,
      status = 'PARTIALLY_FILLED',   ← 状态变更
      updated_at = NOW()
  WHERE id = 12345;

  INSERT INTO trades
  (order_id, price, quantity, fee)
  VALUES (12345, 65000, 0.3, 0.0003);  ← 产生第 1 条成交记录

  剩余 0.7 BTC 保留在订单簿，等待新的卖单

────────────────────────────────────────────────────────
第二次撮合（0.5 BTC 成交）：

  UPDATE orders
  SET executed_quantity = 0.8,       ← 累加，不是覆盖
      status = 'PARTIALLY_FILLED'
  WHERE id = 12345;

  INSERT INTO trades ... (0.5 BTC)   ← 产生第 2 条成交记录

────────────────────────────────────────────────────────
第三次撮合（最后 0.2 BTC 成交）：

  UPDATE orders
  SET executed_quantity = 1.0,
      status = 'FILLED',             ← 全部成交，状态终结
      fill_price = 加权平均价
  WHERE id = 12345;

  INSERT INTO trades ... (0.2 BTC)   ← 产生第 3 条成交记录
```

**整个过程：1 条 order 记录，3 条 trade 记录，order 始终是同一行，不会新增。**

### IOC 订单的处理

```
挂 IOC 买单：1.0 BTC @ 65000
卖盘只有：0.3 BTC

立即撮合 0.3 BTC → executed_quantity = 0.3
剩余 0.7 BTC → 立即 UPDATE status = 'CANCELED'

最终结果：部分成交 + 部分取消（同一条订单记录）
```

### FOK 订单的处理

```
挂 FOK 买单：1.0 BTC @ 65000
卖盘只有：0.3 BTC

检查：0.3 < 1.0，无法全部成交
→ 整单直接 UPDATE status = 'EXPIRED'（或 'CANCELED'）
→ 不产生任何成交记录
```

## 5. 订单状态机

```
           下单
            │
            ▼
          NEW  ─────────────────────────────────▶ CANCELED
         （挂单中）                               （手动撤单 / IOC剩余 / FOK失败）
            │
            │ 首次部分成交
            ▼
   PARTIALLY_FILLED ────────────────────────────▶ CANCELED
         （部分成交中）                           （撤掉剩余部分）
            │
            │ 全部成交
            ▼
          FILLED
         （完全成交，终态）


    另外还有：
      PENDING_CANCEL  → 撤单请求已提交，等待确认中
      REJECTED        → 下单被拒绝（余额不足等）
      EXPIRED         → FOK 未能全部成交 / GTD 超时
```

## 6. 币安的关键数据字段

币安 REST API 查询订单时返回的关键字段：

```json
{
  "orderId": 12345,
  "symbol": "BTCUSDT",
  "side": "BUY",
  "type": "LIMIT",
  "timeInForce": "GTC",
  "status": "PARTIALLY_FILLED",

  "origQty": "1.00000000",            ← 委托总量
  "executedQty": "0.30000000",        ← 已成交量（累计）
  "cummulativeQuoteQty": "19500.00",  ← 已成交的 USDT 总额（累计）

  "price": "65000.00",                ← 委托价格
  "fills": [                          ← 本次请求的成交明细（仅下单时返回）
    {
      "price": "65000.00",
      "qty": "0.30000000",
      "commission": "0.00030000",     ← 手续费
      "commissionAsset": "BTC",
      "tradeId": 78901
    }
  ]
}
```

### 剩余未成交量的计算

$$
\text{剩余量} = \text{origQty} - \text{executedQty} = 1.0 - 0.3 = 0.7 \text{ BTC}
$$

### 加权平均成交价（VWAP）

当订单在多个不同价格层级部分成交时（市价大单），实际均价需要加权计算：

$$
\text{均价} = \frac{\text{cummulativeQuoteQty}}{\text{executedQty}} = \frac{19500}{0.3} = 65000 \text{ USDT/BTC}
$$

## 7. WebSocket 实时推送

币安不需要轮询，每次发生部分成交，通过**用户数据流**（User Data Stream）主动推送 `executionReport` 事件：

```json
{
  "e": "executionReport",           ← 事件类型
  "E": 1700000000000,               ← 事件时间（毫秒）
  "s": "BTCUSDT",                   ← 交易对
  "i": 12345,                       ← 订单 ID
  "X": "PARTIALLY_FILLED",          ← 当前订单状态
  "x": "TRADE",                     ← 本次执行类型

  "l": "0.30000000",                ← 本次成交量（Last filled qty）
  "L": "65000.00",                  ← 本次成交价
  "z": "0.30000000",                ← 累计成交量（Cumulative filled qty）
  "Z": "19500.00",                  ← 累计成交额

  "n": "0.00030000",                ← 本次手续费
  "N": "BTC",                       ← 手续费资产

  "t": 78901                        ← 成交 ID（trade ID）
}
```

前端收到此事件后，直接更新对应订单的 `executedQty` 和 `status`，**无需轮询**。

## 8. 本系统 vs 币安对比

| 维度 | 本系统 | 币安 |
|------|--------|------|
| **成交模型** | 全量一次成交（无真实订单簿）| 逐档撮合，支持多次部分成交 |
| **部分成交状态** | 无 | `PARTIALLY_FILLED` |
| **订单状态** | `pending` / `filled` / `cancelled` | `NEW` / `PARTIALLY_FILLED` / `FILLED` / `CANCELED` / `EXPIRED` / `REJECTED` |
| **时效策略** | 无（等同 GTC）| GTC / IOC / FOK / GTD |
| **成交记录** | 每笔订单固定 1 条 trade | 每次部分成交 1 条 trade，一个订单可有多条 |
| **实时通知** | 前端轮询（每 3 秒）| WebSocket User Data Stream 实时推送 |
| **手续费** | 固定为 0 | Maker/Taker 费率（BNB 折扣等）|
| **滑点** | 零滑点（单一价格成交）| 大单逐档成交产生真实滑点 |

## 9. 本系统升级部分成交的方案

如果要让本系统支持部分成交，需要以下改造：

### 第一步：扩展订单状态

```sql
-- orders.status 新增 'partial' 状态
ALTER TABLE orders
  ALTER COLUMN status TYPE VARCHAR(20);

-- 允许值：'pending' | 'partial' | 'filled' | 'cancelled'
```

### 第二步：修改 fillOrderInEngine

```typescript
async function fillOrderInEngine(
  orderId: number,
  side: string,
  filledQty: number,   // 本次实际成交量（可能 < 委托量）
  fillPrice: number
) {
  // 获取订单委托总量
  const order = await pool.query('SELECT * FROM orders WHERE id = $1', [orderId]);
  const totalQty = Number(order.rows[0].quantity);
  const prevExecuted = Number(order.rows[0].executed_quantity || 0);
  const newExecuted = prevExecuted + filledQty;

  // 更新账户余额（只按本次成交量）
  // ... 账户更新逻辑 ...

  // 判断是全部成交还是部分成交
  const newStatus = newExecuted >= totalQty ? 'filled' : 'partial';

  await pool.query(
    `UPDATE orders
     SET executed_quantity = $1,
         status = $2,
         fill_price = CASE WHEN $2 = 'filled' THEN $3 ELSE fill_price END,
         updated_at = NOW()
     WHERE id = $4`,
    [newExecuted, newStatus, fillPrice, orderId]
  );

  // 每次部分成交都产生一条 trade 记录
  await pool.query(
    'INSERT INTO trades (order_id, price, quantity, fee) VALUES ($1, $2, $3, 0)',
    [orderId, fillPrice, filledQty]
  );
}
```

### 第三步：引擎轮询时跳过已部分成交订单的重复触发

```typescript
// checkPendingOrders 查询条件改为包含 partial
const res = await pool.query(
  `SELECT * FROM orders WHERE status IN ('pending', 'partial')`
);
```

### 改造成本评估

| 改造项 | 难度 | 说明 |
|--------|------|------|
| 订单状态扩展 | 低 | 加一个 `partial` 状态值 |
| `fillOrderInEngine` 改造 | 中 | 累加 `executed_quantity`，按量更新账户 |
| 引擎轮询逻辑调整 | 低 | 查询条件加上 `partial` |
| IOC / FOK 支持 | 中 | 下单入口增加 `timeInForce` 参数判断 |
| 前端展示 `partial` 状态 | 低 | OrderHistory 显示"部分成交"标签 |
| 真实订单簿深度模拟 | 高 | 需要构建内存订单簿，成本最高，非必须 |

> 不引入真实订单簿的情况下，可以模拟"随机成交比例"来近似部分成交效果，从而支持 `partial` 状态和多条 trade 记录，而不需要实现完整的双边订单簿撮合引擎。

## 总结

```
部分成交 = 委托量 > 对手方当前可成交量 → 只成交一部分，剩余继续等待

时效策略决定"剩余怎么办"：
  GTC → 继续挂着（最常见）
  IOC → 剩余立即取消
  FOK → 必须全成，否则整单取消

币安处理方式：
  ├── 同一条 order 记录，累加 executed_quantity
  ├── 状态：NEW → PARTIALLY_FILLED → FILLED
  ├── 每次部分成交产生一条 trade 记录
  └── WebSocket 实时推送，无需轮询

本系统：
  ├── 全量一次成交，无部分成交
  └── 升级路径：扩展 status + 修改 fillOrderInEngine 累加逻辑
```
